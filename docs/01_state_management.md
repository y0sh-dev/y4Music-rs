# 01. State Management Design

## Challenge: Sharing mutable state across guilds without lock mix-ups

This Bot runs simultaneously on multiple Discord servers (guilds). Each guild needs to independently hold mutable states such as "current panel message ID", "loop mode", and "auto-leave timers", and these are accessed concurrently from multiple paths: command processing, button processing, and songbird event handlers. If we naively place a single `Mutex<HashMap<GuildId, State>>`, a prolonged process in one guild will block processes in completely unrelated guilds.

## `GuildPlayers`: DashMap + Nested Async Mutex

```rust
// player.rs
pub type GuildPlayers = DashMap<serenity::GuildId, Arc<Mutex<GuildPlayerState>>>;
```

`dashmap::DashMap` is internally a collection of `RwLock`s divided into multiple shards. Since different keys acquire locks on different shards, processing for Guild A does not block Guild B. Up to this point, it's just a "fast HashMap", but there is a reason why the value type is `Arc<Mutex<GuildPlayerState>>` instead of just `GuildPlayerState`.

### Why wrap it doubly?

The guard (`Ref`) returned by `DashMap::get()` is a **synchronous** lock guard. If you hold this across a `tokio` `.await` point, that shard becomes invisible to other tasks. If another task happens to access a different key in the same shard during the `.await`, a deadlock will easily occur.

Therefore, all calls must follow this procedure:

```rust
// 1. Release the DashMap guard the moment Arc is cloned (exits scope)
let Some(state_arc) = guild_players.get(&guild_id).map(|e| e.clone()) else {
    return;
};
// 2. From here on, it's a tokio::sync::Mutex lock. Safe to cross .await.
let mut state = state_arc.lock().await;
```

```text
[DashMap shard lock]  Synchronous / Short-lived
        │  Drop immediately after extracting Arc via .clone()
        ▼
[Arc<Mutex<GuildPlayerState>>]  Asynchronous / Awaitable
        │  .lock().await
        ▼
[&mut GuildPlayerState]  .await can be safely used from here onwards
```

This two-stage pattern appears repeatedly in almost all functions in `player.rs` (`refresh_panel` / `sync_idle_leave_task` / `handle_component_interaction`, etc.). It may look redundant at first glance, but it should be understood as a boilerplate to maintain the invariant: "Never hold a DashMap synchronous guard and an `.await` at the same time."

## 4 Timers and 1 Flag in `GuildPlayerState`

| Field | Role | Start Trigger | Stop Trigger |
|---|---|---|---|
| `empty_channel_leave_task` | Auto-leave after no humans are left in the voice channel (30s) | Detected 0 people in `handle_voice_state_update` | Someone rejoins / `cleanup_guild` |
| `idle_leave_task` | Auto-leave after the queue becomes empty (600s) | `sync_idle_leave_task` (Re-evaluated on every Play/End event) | New track starts playing / `cleanup_guild` |
| `progress_ticker` | A loop that just updates the panel's progress bar every 15s | `TrackEvent::Play` (`ensure_progress_ticker`) | `TrackEvent::End` / Various stop paths |
| `last_button_press` | Timestamp for the 1.5s cooldown of panel buttons | Updated on every button press | (No lifespan, comparison only) |
| `silence_auto_paused` | Flag indicating if everyone is speaker-muted | Detected everyone deafened | At least 1 person undeafens |

Note that `empty_channel_leave_task` and `idle_leave_task` are similar but independent concepts — the former is "are there people in the channel", and the latter is "are there tracks in the queue". If it's empty but a track is playing, only the former runs; if there are people but the queue runs out, only the latter runs.

All these timers hold a `JoinHandle` generated by `tokio::spawn`, and cancellation is done via `abort_unless_self` (see `04_pitfalls.md`). This is not a simple `.abort()` — the reason is the task self-cancellation problem itself, which is detailed in that document.

## Another Instance of the Same Pattern: Session DashMaps

The same design decision as `GuildPlayers` is used for other short-lived states. However, these store raw values instead of `Arc<Mutex<..>>`, and instead manage their lifespan by "holding a creation time and periodically sweeping them in bulk".

```rust
// commands/search.rs
pub type SearchSessions = DashMap<serenity::MessageId, SearchSession>; // Search results for /search

// pagination.rs
pub type ListSessions = DashMap<serenity::MessageId, ListSession>;     // Pagination for /playlist_show, etc.
```

Both use the "message ID" as the key and are referenced only when a button on that message is pressed. Unlike `GuildPlayers`, there is no natural overwrite/expiration point (the upper limit is not fixed like the number of guilds), so `main.rs::spawn_session_sweeper` calls `sweep_stale` every 5 minutes to delete entries where `created_at.elapsed() > SESSION_MAX_AGE` (15 minutes) to prevent memory leaks.

The consistent design policy is to use `Arc<Mutex<..>>` + event-driven explicit cleanup for "a small number of constantly active guild states", and raw values + time-based bulk sweeping for "temporary sessions waiting for user input".
